# 記事案出しワークフロー

技術ブログの**新規記事案を N 件挙げる**スキル。案出しのみで、記事の執筆・PR・公開は含まない(それらは `article-workflow` スキル)。

> **言語ルール:** ユーザーへの発信(質問・記事案など)はすべて **日本語** で行う(`CLAUDE.md`)。

## 前提として必ず読むもの

- `docs/rules/article/common.md` — 技術記事作成 共通ガイドライン(リポジトリ前提・テーマの焦点・量産型回避・既存記事の把握方法など)

案の粒度・テーマ選定は、この共通ガイドラインに完全準拠させる。文体・構成の詳細ルール(`guidelines.md` 等)は案出し段階では概要把握で足りるが、必要に応じて参照する。

---

## 手順

1. **件数を確認する。** ユーザーが件数(N)を指定していればそれに従う。指定が無ければ **20 件**を既定とする。

2. **既存記事を実ファイルから把握する(重複回避)。** **まず最新のリモート追跡ブランチを取得する。**
   直近マージされた記事を見落として重複提案しないため、必ず最新化してから確認すること。
   作業ブランチを切り替えず(`checkout`/`pull` しない)、`git fetch origin` で最新を取得したうえで、
   `origin/main` のツリーから直接 slug を列挙する。そのうえで `common.md` §7 に従い、
   `_articles_en/` と `_articles_ja/` のファイル名(= slug)を確認する。

   ```bash
   git fetch origin
   git ls-tree -r --name-only origin/main -- _articles_en _articles_ja \
     | awk -F/ '$NF ~ /\.md$/ {sub(/\.md$/, "", $NF); print $NF}' | sort -u
   ```

   必要に応じて既存記事のフロントマター(`title` / `category` / `excerpt`)を読み、テーマの傾向と既出範囲を把握する。
   このときも作業ツリーではなく、slug 列挙と同じ `origin/main` のツリーから読む(例: `git show origin/main:_articles_ja/<slug>.md`)。
   slug とフロントマターの参照元を最新 `main` に統一し、最新記事の傾向を正しく把握する。

3. **既存記事の補強候補を把握する。** `common.md` §8 に従い、次で補強が必要な記事を列挙する。

   ```bash
   # 「検証環境」を明記していない記事:
   grep -L -E '^- (検証環境|計測環境)' _articles_ja/*.md | xargs -n1 basename | sed 's/\.md$//' | sort
   # 実行画面（PNG）を参照していない記事:
   grep -L 'src="/images/[^"]*\.png"' _articles_ja/*.md | xargs -n1 basename | sed 's/\.md$//' | sort
   # tools/screenshot-capture にシーンが無い記事（図を再生成できない）:
   comm -23 \
     <(ls _articles_ja/*.md | xargs -n1 basename | sed 's/\.md$//' | sort) \
     <(grep -rho 'public string Slug => "[^"]*"' tools/screenshot-capture/Scenes/ | sed 's/.*"\(.*\)"/\1/' | sort)
   ```

   **新規テーマより既存記事の補強を優先する**(`common.md` §8)。N 件のうち、少なくとも半数は補強案にする。
   両方のコマンドに該当する記事を最優先とする。

4. **案を N 件作る。** `common.md` の制約(WPF / C# 特化、トラブル解決・解説型が主軸、1 記事 1 テーマ、既存 slug と重複させない、量産型回避)を満たすテーマを選ぶ。
   - 各案は「その 1 テーマで日英ペア 1 本」を書ける粒度にする。
   - slug は英小文字・ハイフン区切りで、既存ファイル名と重複しない一意なものにする。
   - シリーズ化する案には「同一言語の関連記事へ内部リンクする」旨を添える(日英カウンターパート間はリンクしない)。
   - **補強案では、対象の既存 slug と「何を実測で確かめるか」を具体的に書く。** 新しい slug は作らない。

5. **出力する(下記の形式)。**

---

## 出力形式

各案を「**別セッションにそのまま貼れる指示文**」として、次の形式で N 件挙げる。番号付きリストにし、カテゴリ(WPF / C#)ごとに緩くグループ化してよい。

**新規記事の案:**

```text
テーマ: <扱う技術と解決する問題を具体的に>。記事タイプ: <問題解決型 or 手順・解説型>。
slug: <英小文字ハイフンの一意な slug>。category: <WPF or C#>。
実行モード: 手動(内容確認あり)。日英ペアで作成。
```

**既存記事の補強案**(`common.md` §8):

```text
補強: <対象の既存 slug>。
検証する主張: <記事が断定していて、まだ実測で確かめていない記述>。
実測方法: tools/screenshot-capture に <シーン名> を追加し、<何をどう測るか>。
実測が記述と食い違った場合は記事のほうを修正する(guidelines.md §12.1)。
実行モード: 手動(内容確認あり)。日英ペアで修正。
```

- 各案は 1 行(または論理的に 1 まとまり)で、`article-workflow` スキルにそのまま渡せる指示として完結させる。
- シリーズ化する案には「同一言語の関連記事へ内部リンクする」の一文を添える。

最後に、次の短い補足を付ける。

- 各指示は `article-workflow` スキルを想定した形式であること。
- **新規テーマより既存記事の補強を優先する方針であること**(`common.md` §8)。補強案は分量を増やすためではなく、未検証の記述を実測で確かめるためのものである。
- 実行モードは既定を「手動(内容確認あり)」とし、任せる場合は「オート」、PR 前で止める場合は「PR 前まで」に置き換えられること。
- slug は日英で同一ファイル名になり、既存記事とは重複しないよう命名済みであること。
- シリーズ化する案は、連番タイトルを避けて各記事固有のテーマ名で書き、各記事に独自の背景・注意点・比較を持たせること(独自性の確保)。そのうえで同一言語の記事どうしのみ相互リンクする(内部リンク方針)。量産型扱いの回避は独自性など品質要件の充足が前提であり、内部リンク単独で保証されるものではない。
