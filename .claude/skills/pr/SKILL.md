# PR 作成・レビュー対応・マージ ワークフロー

作業ブランチ上の変更に対して **PR 作成 → レビュー待ち → 指摘修正 → 再レビュー依頼(ループ)→ マージ** を実行するスキル。
記事作成は含まない。既にコミット済み(または本セッションでコミットできる)変更があり、それを PR にして公開まで持っていく場面で使う。

> **言語ルール:** ユーザーへの発信(質問・進捗報告・PR 説明文・コミットメッセージなど)はすべて **日本語** で行う(`CLAUDE.md`)。
>
> **参考:** レビュー対応・マージの手順は `article-workflow` スキルの Phase 4・5 に準拠する。
> 本スキルはその PR 以降の部分を単体で実行するためのもの。

---

## Phase 1. コミット & プッシュ

1. **push の前に(可能ならコミットの前に)、文脈を持たないサブエージェントで独立レビューする。**
   CodeRabbit の再レビューには回数制限がある(Phase 3 手順 3)ため、push 前に拾える指摘は先に潰す。
   書いた本人は意図を知っているぶん食い違いを見落とすので、会話の文脈を引き継がないサブエージェントに見せる。
   - **対象:** push するすべての差分に行う。例外は、`article-workflow` の Phase 2(手順 5 の `/code-review high` まで)が
     収束したあと、1 行も変更していない差分を push する場合だけとする(`article-workflow` の Phase 3 の「修正あり」で Phase 2 に戻り、収束し直した場合も含む)。
     `article-workflow` の Phase 2 のあとに CI の修正・PR 上のレビュー指摘への対応などで直した場合は、記事だけの変更でも、
     直した後の差分に行う。`/code-review high` の再実行はこの独立レビューの代わりにしない。
     main の取り込み(rebase・merge)の後の push は、競合の有無にかかわらず独立レビューを通す
     (競合が無くても、main 側の変更でこのブランチの記述の前提が変わることがあるため)。上の例外より優先する。
     ただし `article-workflow` の Phase 1(記事を書く前)の取り込みは、その後の Phase 2 のレビューに含まれるので、この規則には当たらない。
     この条件は `article-workflow` からも参照する。
   - **レビュアーを起動する前に、依頼者がリポジトリのルートで次を順に実行する。** 出力の置き場は、各スクリプトが標準出力に表示するパス
     (`git rev-parse --git-path review-gate` の場所。通常は `.git/review-gate/`、worktree ではその worktree 用の場所。コミットされない)。
     作業ツリーを書き換えうるコマンド(生成・整形など。下の共通の指示で「作業ツリーを書き換えるコマンド」として依頼者が実行するもの)は、
     この前に実行して `git status` で確かめておく(`approve.mjs start` の後に作業ツリーが変わると、承認できない)。
     コミットしない未追跡のファイル(作業メモなど)も、この前に片付ける(承認する内容に含まれ、push の照合で一致しなくなる)。
     0. `node tools/review-gate/setup.mjs` … pre-push フックを有効にする。クローンごとに 1 回でよい(既に有効なら何もしない。
        Web 実行環境ではセッションの初めに実行する)。
     1. `node tools/review-gate/article-check.mjs` … 機械で確かめられることを `article-check.md` にまとめる。
        断定語を含む行(Markdown と、C#・JavaScript の行頭がコメントの行)、記事の比率・比較の文とその記事が読み込む表、
        記事のコード片(C# は 1 つずつコンパイル、XAML は XML として読めるか)、
        変更した C# のメソッドと JavaScript の関数の説明コメントの割合(CodeRabbit の Docstring Coverage とは数え方が違う参考値)。
        コード片に「構文・型の誤りの可能性」「存在しないメンバーを呼んでいる」「XML として読めない」が出たら、
        レビュアーを起動する前に直して実行し直す(抜粋として正しいのに出た場合は、理由をレビュアーに伝えて進めてよい)。
        「包み方で確かめられない」「抜粋の外で宣言された名前を参照しているだけの可能性(要確認)」が出たら、そのコード片をレビュアーに伝えて確かめさせる。
        コード片 1 つにつき最大 4 回ビルドするので、コード片の多い記事では数分かかる。
        「確かめていない」が出た場合(.NET SDK が無い・ビルドできない・Windows 以外で WPF を扱えないなど)は、その範囲をレビュアーに伝える。
     2. `node tools/review-gate/coderabbit-findings.mjs` … 作成が新しい 45 件のうちマージした日時が新しい 15 件の PR で CodeRabbit が付けた指摘
        (インラインの指摘と、レビュー本文の項目(差分の外・Nitpick など。区分は見分けない)、失敗・警告になった pre-merge check)を
        `coderabbit-findings.md` にまとめる。このリポジトリでは CodeRabbit が同じ型の指摘を繰り返しているため。
        同じ PR の中で 2 回目以降のレビューをするときは、`coderabbit-findings.mjs` 自体を変えていなければ実行し直さなくてよい。
     3. `node tools/review-gate/approve.mjs start` … レビューしてもらう内容(作業ツリー)を記録する。最後の承認で、承認する内容が
        レビューした内容と同じことを確かめるのに使う。
     - setup.mjs・article-check.mjs・approve.mjs start のどれかが失敗したら、レビュアーを起動せずに原因を直す(下の差分の取得の失敗と同じ扱い)。
       coderabbit-findings.mjs が `gh` を使えずに失敗したら、その旨をレビュアーに伝えて進めてよい。
   - **観点ごとに 3 人のレビュアーを同時に起動する。** 3 人それぞれに、下の共通の指示(差分の取り方から指摘の形式まで)と、
     article-check.md・coderabbit-findings.md のパス(スクリプトが表示したもの)と、担当の観点を 1 つ渡す。
     3 人とも coderabbit-findings.md を読み、同じ型の問題が差分に無いかを確かめる。
     1. **主張の範囲と数値:** article-check.md の断定語と比率の行をもとに、各文の比率・大小・断定が、表の値と計測の条件で成り立つかを計算して確かめる。
        中央値だけで成り立つ比較に「中央値で」と書いてあるか。測っていない条件にまで言い切りを広げていないか。
     2. **コードと API の事実:** 記事のコード片と変更したコードが、流用されたとき(自分自身を渡す・別スレッドから使う・空の入力など)に壊れないか。
        API の動作・既定値・導入バージョンの説明が、公式ドキュメント(Microsoft Learn)や dotnet のソースと合っているか(確かめた URL を指摘に書く)。
        article-check.md のコード片と説明コメントの結果も見る。
     3. **規約・一貫性・日英:** 下の「少なくとも次の観点」と、日英の内容の一致。
        (「少なくとも次の観点」は 3 人目の担当として渡す。ほかの 2 人には共通の指示の一部として渡し、担当外は気づいた分だけ書かせる)
     - 経緯:PR #174 では 1 人のレビュアーに全部を見させ、7 回通しても、記事のコード片が自分自身を渡されると壊れることと、
       コメントのスレッド安全性の言い過ぎを見落とし、どちらも CodeRabbit に指摘された。
   - `Agent` ツールで、文脈を引き継がない種別(`general-purpose` など。fork は使わない)を起動し、共通の指示として次を渡す。
     `isolation: "worktree"` は指定しない(一時コピーが作られ、消される。下の経緯を参照)。
     - 対象リポジトリのパス・ブランチと、差分の取り方(`git fetch origin main` のあと
       Bash(Git Bash)で `mb=$(git merge-base origin/main HEAD) && git diff --ignore-cr-at-eol "$mb"`。未コミットの変更を含める。
       分岐点と比べるのは、ブランチを切った後に main へ入った変更を、このブランチの変更として読まないため。
       `git diff ... $(git merge-base ...)` と 1 つに書くと、merge-base が失敗しても空のまま `git diff` が動いて失敗に気づけないので、分けて書く)と、
       未追跡の新規ファイルの一覧(`git status --short --untracked-files=all`)。新規ファイルは `git diff` に出ないため、一覧を渡して読ませる。
       これらの差分と一覧を取るコマンドが 1 つでも失敗したら、レビューをせずにその旨を報告すること
       (依頼者が一覧を取れなかったときは、レビュアーを起動しない)
       (`git fetch` に失敗すると、最新の `origin/main` を取れたと確かめられず、比べる相手の新しさと正しさを保証できないため。
       下の「未実行(推論)」の扱いは使わない)
     - **レビュー範囲は PR の差分全体とすること。** 指摘への修正を push する前でも、直した箇所だけに絞らない。
       直した箇所を重点的に見てほしいときは、範囲を狭めずに「特に見てほしい箇所」として添える
     - `.coderabbit.yaml` の `path_instructions` を読み、同じ基準で見ること
     - CodeRabbit がレビュー基準として自動で読むガイドラインを読み、同じ基準で見ること。
       リポジトリルートと変更ファイルの上位ディレクトリにある `CLAUDE.md` / `AGENTS.md`、
       および存在すれば `.claude/rules/**/*.md`
     - 変更ファイルが参照している規約と、変更箇所を参照している側も読むこと
     - (あれば)依頼者が元の作業ツリーで実行したコマンドと、その終了コード・生成物
     - **差分で追加・変更した手順・チェックリスト・スクリプトのヘッダーコメントにあるコマンドは、書かれた場所から
       書かれた順に実行して確かめること。** 変更していない前段(`cd` や前提のインストールなど)も含めて手順の頭から実行し、
       前のコマンドで移った作業ディレクトリを引き継いで、パスが解決できるか、終了コードが書かれたとおりになるかを見る。
       説明のための例示コマンドは対象外
       - **作業ツリーを書き換えるコマンド(生成・整形・`npm ci` など)は実行しない。`git worktree` で一時コピーも作らない。**
         依頼者から実行結果を渡されていればそれを使い、渡されていなければ「未実行(推論)」として扱う。
         (この確認は依頼者が行う:依頼者は実行の前に変更をコミットし、作業ツリーで実行して、その結果を渡す。
         実行後に `git status` で作業ツリーが元のままかを確かめ、変わっていれば、その差分も含めて独立レビューをやり直す)
       - **レビュアーは、作業ツリーでコミット・ステージ・ファイルの変更をしない**
       - 外部への書き込みは実行しない。push・PR やコメントの投稿・マージ・外部サービスへの送信が該当する。
         パッケージの取得など読み取りだけの通信は、確かめる対象の手順に書かれている場合に限り実行してよい
       - 実行できなかったコマンドは、手順を読んで推論でたどり、指摘に「未実行(推論)」と書き添える
     - 承認の記録・生成物の置き場(`git rev-parse --git-path review-gate`)と git の設定を書き換えるコマンド
       (`setup.mjs`・`approve.mjs`・`article-check.mjs`・`coderabbit-findings.mjs` の実行を含む)は実行せず、「未実行(推論)」とすること
       (3 人が同時に動くので、依頼者の記録やほかのレビュアーの材料を上書きしないため)
     - レビュアーの Bash・PowerShell のコマンドも `check-setup.mjs` の hook を通るので、「push」と照合を外す語の両方を含むコマンド
       (例: その 2 語で探す grep)は止まる。文字列の検索は Grep ツールを使うこと
     - 上の実行を除き、読むだけでファイルを変更しないこと
     - 指摘は件数を絞らず、各指摘に「ファイル:行」「何が問題か」「直し方」「重要度(要修正 / 軽微 / 見送り可)」を付けること
   - 少なくとも次の観点を確認させる。
     - **同じ規則を書いた箇所どうしが一致しているか。** 語・項目・条件・例外が食い違っていないか。
       変更した規則を、変更していないファイルが古い定義のまま書いていないか(規則のキーワードで全体を `grep` させる)。
       同じ規則を複数の場所に書き写していないか(書き写すと、片方を直したときにずれる。規則は 1 か所に書き、他からは参照する)
     - **番号と参照。** 節番号・手順番号の並びと、それを参照している箇所が合っているか
     - **主張と根拠の強さ。** 「仮説」「未検証」とした内容を、別の文で断定していないか
     - **基準が具体的か。** 期間・閾値・対象が日付・数値・パスで特定できるか。期間どうしが矛盾していないか
     - **PR 自身が足した規則に、PR 内の変更が従っているか**
     - **字数・件数の上限。** レビュアー自身がスクリプトで測って確かめる
     - **体裁。** markdownlint(`.markdownlint.json`)に通るか。記事を含む場合は `docs/rules/article/guidelines.md` §9 の改行規則にも従うか
   - **重要度の扱い:** 次の 3 種類は、レビュアーが軽微・見送り可と付けても要修正として扱う(レビュアーにもそう伝える)。
     CodeRabbit は重要度が Minor でも直すまで指摘を残すので、ここで見送ると PR 上で同じ指摘を受け、再レビューを 1 時間待つことになる。
     - 主張が、測った範囲・条件・実装を超えている
     - 記事のコード片・手順・スクリプトが、流用や手順どおりの実行で壊れる・詰まる
     - 事実の誤り(API の動作・既定値・導入バージョンを含む)
     - 経緯:PR #174 では、空でないコレクションに `Reset` を通知したときの影響を独立レビューが「軽微」として挙げていたのに、
       条件を書き足すだけにして、CodeRabbit に指摘された。
   - **止める条件:** 要修正はすべて直し、修正後の PR の差分全体を同じ条件で再びレビューさせる
     (`article-check.mjs` と `approve.mjs start` を実行し直してから。直したコード片の結果をレビュアーの材料に反映するため)。
     要修正が無くなるまで繰り返す。
     軽微・見送り可は、直すか、見送る理由を残す。直すなら要修正と一緒に直して次の回のレビューに含める。
     要修正が 0 件になった回の軽微を直すなら、直した後にもう 1 回レビューを通す(承認する内容は、レビューした内容と同じでなければならない)。
     見送る理由は、PR を作る前なら、PR 作成時に PR 説明へ書く
     (このスキルの Phase 2 手順 2 / `article-workflow` の Phase 4 手順 2)。
     PR が既にある場合(PR 作成後の修正 push など)は、PR へのコメントか PR 説明の更新で残す。
     どちらの場合もユーザーへ報告する。判断の原則の「指摘は件数を絞らない」は PR 上のレビュー指摘についてのもので、
     この独立レビューには適用しない(assertive に広く挙げさせるため、軽微なものまで直すと収束しないことがある)。
   - **要修正が 0 件になったら、依頼者が `node tools/review-gate/approve.mjs done "<結果の要約>"` で承認を記録する。**
     作業ツリーが `approve.mjs start` の時点と違えば(レビューの後に変えていれば)記録されないので、`start` からレビューをやり直す。
     上の「対象」の例外(`article-workflow` の Phase 2 の収束後に 1 行も変えずに push する場合)は、
     手順 0 の `setup.mjs` を済ませ、`node tools/review-gate/article-check.mjs` を実行し、報告の (c) に上の 1.(`article-check.mjs`)で挙げた 3 種の誤り(構文・型の誤りの可能性、存在しないメンバー、
     XML として読めない)が出ていないことを確かめてから(出たら直す。直したら例外ではなくなる。
     抜粋として正しいのに出た場合と、確かめる人のいない「包み方で確かめられない」「要確認」「確かめていない」が出た場合は、
     例外をやめて独立レビュー(start〜done)に切り替える)、
     `node tools/review-gate/approve.mjs direct "article-workflow の Phase 2 で収束"` で記録する。
   - **承認と push の照合(仕組み):** git の pre-push フック(`.githooks/pre-push` → `tools/review-gate/pre-push.mjs`)が、
     push される各ブランチの先頭のコミットの内容(ツリー)を承認の記録と照合し、違えば push を止める。
     照合が保証するのは「push する各ブランチの先頭のコミットの内容が、承認した内容と同じこと」だけで、
     間のコミットの内容や、レビューが行われたことまでは確かめない。
     - フックが動けば、照合する ref は git が渡すので、コマンドのつなぎ方やブランチの指定には左右されない。
       削除と、送り先がブランチ(refs/heads/)以外の push(タグなど)は照合しない。送り元がタグでも、送り先がブランチなら照合する。
     - 照合するのは環境変数 `CLAUDECODE=1` の環境(Claude Code の Bash・PowerShell ツール、hook の子プロセス、Claude Code の IDE 拡張の
       統合ターミナルなど。<https://code.claude.com/docs/en/env-vars> の `CLAUDECODE` の行による)からの push だけ。
       IDE 拡張の統合ターミナルから人が push した場合も照合する。それ以外の端末から人が push するときは照合しない。
     - フックは `node tools/review-gate/setup.mjs` で有効にする(`core.hooksPath` を `.githooks` の絶対パスにする。クローンごとに 1 回)。
       絶対パスにするのは、`.git` の中や `--git-dir`・`GIT_DIR` で作業ツリーのルートが変わった push でもフックを動かすため。
       そうした push は、作業ツリーのルートを特定できないか、そこに照合のスクリプトが無ければ、フックの sh 側が止める(あれば照合する)。
       `core.hooksPath` は同じリポジトリの worktree の間で共有されるので、別の worktree で setup を実行しても、
       既にこのリポジトリのチェックアウトのルート直下の `.githooks`(pre-push のあるもの)を指していれば変更せずに終わる。
       指す先が pre-push の無い `.githooks` なら置き換える(判定に使うのはこのクローンの設定(`--local`)だけで、
       グローバルやシステムの `core.hooksPath` はローカルの設定で上書きする。最後に実際に効いている値を確かめ、
       worktree 単位の設定や include で読み込んだ値が効いていれば、その出どころを表示して止める)。同じリポジトリの別の worktree が `.githooks` の無いブランチにあり、そこから push した場合は、
       フックは動き、照合のスクリプトが無いので sh 側が止める。
     - `.claude/settings.json` の hook(`tools/review-gate/check-setup.mjs`)は、Bash・PowerShell のコマンドの文字列を、
       シェルの構文を解析せずにそのまま見て、次のときに止める(解析すると書き方の穴が尽きないので、迷う場合は止める側に倒す)。
       - コマンドに「push」を含み、`$CLAUDE_PROJECT_DIR` のリポジトリでフックが有効でない(core.hooksPath がこのリポジトリのチェックアウトのルート直下の、pre-push のある `.githooks` の絶対パスであることと、
         今のチェックアウトに `.githooks/pre-push` があることの、どちらかが欠けている)
       - コマンドに「push」を含み、照合を外す語(`--no-veri`、`hookspath`、`CLAUDECODE`、オプションを付けた `env` など。全体は `check-setup.mjs` の冒頭)も含む。
         語の一覧は網羅ではない。メッセージや引用符・ヒアドキュメントの中に書いた語でも止まるので、そうした語を含むコミットメッセージは、
         作業ツリーの外(一時ディレクトリなど)に置いたファイルから `git commit -F "<ファイル>"` で渡す
         (作業ツリーの中に置くと、手順 2 の `git add -A` でコミットに入り、承認した内容と一致しなくなる)。
         そのファイルは Write ツールで作る(Bash・PowerShell のヒアドキュメントや echo で書くと、そのコマンドが同じ理由で止まる)。
         `gh` で PR を作る場合の本文も同じく `--body-file "<ファイル>"` で渡す(MCP のツールで作る場合は、この hook の対象外)
     - **仕組みで防げないもの:**
       - `--no-verify`・`core.hooksPath` の変更、`core.hooksPath` の指すチェックアウト(通常は `$CLAUDE_PROJECT_DIR`)を
         `.githooks` の無い(照合の仕組みが入る前の)ブランチやコミットに切り替えた後(同じコマンドの中でも、別のコマンドでも。
         切り替えると `check-setup.mjs` も無くなるので、hook の設定が残っていても実行できず、上の hook では止められない)ではフックが動かず、
         `CLAUDECODE` を外した実行ではフックは動くが照合しない
       - 上の hook はコマンドの文字列だけを見るので、一覧に無い語や書き方(オプションの別の綴りなど)、
         変数・別名・スクリプトの中で組み立てる操作は止められない
       - フックを有効にしていない別のクローン(`cd`・`git -C` で移った先)からの push は、`check-setup.mjs` によるフックが有効かの確認も、pre-push の照合も効かない
         (照合を外す語の確認は効く)
       - 照合のフック・スクリプト(`.githooks/pre-push`・`tools/review-gate/*.mjs`)や承認の記録を書き換えてから push すると照合が外れる
         (フックは作業ツリーのスクリプトを実行するので、コミットしていない書き換えでも外れる)
       - git を通さずにリモートのブランチを書き換える操作(GitHub の API・MCP のツール・`git send-pack` など)と、
         Bash・PowerShell 以外の経路は照合されない
       - どれも手順として使わない
     - 仕組みを変えたら `node tools/review-gate/test-gate.mjs` を実行し、すべて OK になることを確かめる。
     - 経緯:PR #174 では、最初の push の前に測り直して本文の倍率を書き換え、その後に独立レビューを通さずに push して、
       その倍率を CodeRabbit に指摘された。手順に書いてあっても守れなかったので、仕組みで止めるようにした。
       最初は Claude Code の hook でコマンドの文字列から `git push` を探す形にしたが、この PR の独立レビューで、
       `--dry-run` を除くための判定が後ろの `| tail -n 5` の `-n` に当たって通すことや、`git -c ... push` を見逃すことが分かり、
       pre-push フックで照合する形に変えた。
   - **CodeRabbit の代わりではない。** マージの条件は引き続き Phase 4 のマージ直前チェックリストとする。
   - 経緯:PR #165(既存記事の `seo_title` 修正と、タイトルのレビュー観点の規約への追加)は、この手順を入れずに push した。
     CodeRabbit が規約どうしの表記ゆれや曖昧な期間指定を 1 回に 1〜5 件ずつ指摘し、再レビューのたびに 1 時間待った。
     途中でこの手順を試したところ、同じ種類の指摘が 1 回でまとめて見つかった。
     PR #168(OGP 画像)では push のたびにこの手順を通したが、指摘への修正の push 前に直した箇所だけを見させ、
     コマンドも実行させていなかった。CodeRabbit は差分全体から 3 件、次の回にも 1 件
     (チェックリストのコマンドを書かれた順に打つと存在しないパスを探す)を指摘し、そのたびに 1 時間待った。
     範囲を差分全体に固定することと、コマンドを書かれた順に実行させることは、これを受けて足した。
     書き込みの禁止範囲は、この追加の PR(#169)への CodeRabbit の指摘を受けて足した(同じときに一時コピーの作り方と後始末も足したが、下の PR #170 を受けて外した)。
     PR #170 では、レビュアーが一時コピー(`git worktree`)をスクラッチの長いパスに作り、`git worktree remove --force` が
     `Filename too long` で失敗した。その直後に元のリポジトリが `.git` ごと空になった(原因は特定できていない)。
     これを受けて、レビュアーには一時コピーを作らせず、書き換えを伴うコマンドは依頼者が実行して結果を渡す形にした。
     一時コピーの置き場や後始末を細かく定める案は、PR #171 で試したが、手順が膨らみ、CodeRabbit の指摘が回ごとに続いたため、ユーザーの判断でやめた。

2. **変更をコミットする。** 手順 1 で直した分を含め、未コミットの変更があればコミットする。
   承認した内容は作業ツリー全体(未追跡のファイルを含む)なので、一部だけをステージせず `git add -A` でそのまま全部コミットする
   (一部だけだと、push の照合で一致しない)。
   追加の変更が無い場合はコミットを省略する(`nothing to commit` で止めない)。

3. **プッシュする。** `git push -u origin "<branch>"` で作業ブランチへ push する。
   - ブランチ名は必ずクォートして渡す(シェルのメタ文字によるコマンドインジェクションを防ぐ)。
   - push を止められたら、表示された理由に従う。主な理由は次のとおり。フックを外したり `--no-verify` を付けたりして push しない。
     - フックが有効になっていない、または今のチェックアウトに `.githooks/pre-push` が無い(check-setup.mjs)
     - 作業ツリーのルートを特定できない、またはそこに照合のスクリプトが無い(フックの sh 側)。
       `.git` の中や `--git-dir` での push ならリポジトリのルートから push し、照合の仕組みが入っていないブランチなら main を取り込む
     - 「push」を含むコマンドに、照合を外す語を含んでいる(メッセージやブランチ名の中の語でも止まる。メッセージはファイルから渡し、
       ブランチ名に含むならブランチ名を変える)(check-setup.mjs)
     - 承認の記録が無い・読めない・tree が無い(pre-push.mjs)
     - push するコミットの内容が承認と違う(承認の後の変更、承認のときにあった未追跡のファイルのコミット忘れ、内容の違う別のブランチ)(pre-push.mjs)
     - git から渡された push の内容を読めない、または照合の途中でエラーが起きた(pre-push.mjs)
   - ネットワークエラー時は 2s/4s/8s/16s の指数バックオフで最大 4 回リトライする。
   - **push に成功してから Phase 2 へ進む。** 4 回の再試行をすべて失敗した場合、またはネットワーク以外の
     エラー(認証・権限・非 fast-forward 等)が発生した場合は Phase 2 へ進まず、処理を中止してユーザーへ報告する。
     リモートに最新コミットが無いまま古い内容で PR を作成・再利用しないためのガードである。
   - 未 push のコミットが残っていれば push してから Phase 2 へ進む。

## Phase 2. PR 作成

1. **既存の PR を確認する(重複作成の防止)。** PR 作成前に、現在のブランチから `main` 宛ての
   オープンな PR が既に存在しないかを `mcp__github__list_pull_requests`(`head` にブランチ、`base` に `main` を指定)で検索する。
   - **ベースが `main` の PR だけを対象にする。** `head` だけで絞ると、同じブランチから別ベース向けに
     作られた PR を誤って再利用しかねない。`base` でも絞るか、返却結果の `base.ref == "main"` を必ず確認する。
   - **既にオープンな `main` 宛て PR があれば、それを再利用する。** `create_pull_request` は再実行せず、その PR 番号で
     手順 3(購読)へ進む。Phase 3 のフォールバックからセッションを再開した場合など、重複した PR や
     購読を作らないためのガードである。
   - 該当するオープンな PR が無い場合のみ、手順 2 で新規作成する。

2. **PR を作成する。** GitHub MCP(`mcp__github__create_pull_request`)で `main` 宛の PR を作成する。
   - リポジトリに PR テンプレート(`.github/pull_request_template.md` 等)があれば、その見出し構成に沿って本文を埋める。
   - タイトル・本文は日本語で記述する。変更内容を要約し、テンプレートの各節を埋める。

3. **PR を購読する。** `subscribe_pr_activity` で PR を購読し、以降のイベント
   (CI 結果・レビューコメント)を `<github-webhook-activity>` として受け取れるようにする。

4. **購読直後に PR 状態を再取得して同期する。** PR 作成から購読までの間に CI や自動レビューが
   始まる/完了することがあり、その分の Webhook を取りこぼす可能性がある。購読直後に
   `mcp__github__pull_request_read`(`get_status` / `get_check_runs` / `get_review_comments`)で
   状態を再取得し、既に発生済みの CI 結果・レビュー指摘を Phase 3 に持ち込む。

## Phase 3. レビュー待ち → 指摘修正 → 再レビュー依頼(指摘ゼロまでループ)

**指摘が無くなるまで**、以下 1〜5 を繰り返す。

1. **レビューの Webhook 通知を待つ。** PR 作成後、CodeRabbit 等の自動レビューが始まる。
   - **`sleep` でのポーリングはしない。** レビューコメントや CI 結果は
     `<github-webhook-activity>` イベントとしてこのセッションに届く。イベントの到着を待つ。
   - **`send_later` でのセルフチェックイン予約は行わない。** CI 成功・新規 push・マージコンフリクトの
     遷移は Webhook で届かないことがあるが、`sleep` ポーリングも `send_later` 予約もしない。
     長時間反応が無い場合はユーザーへ指示を仰がず、`mcp__github__pull_request_read`
     (`get_status` / `get_check_runs` / `get_review_comments`)で状況を確認し、Phase 3 を続行する。

2. **自動レビューボットの完了を必ず待つ。** `coderabbitai` などはレビュー要求後に処理が走り、
   完了まで数分かかる(CodeRabbit は `auto_incremental_review: false` のため push だけでは再レビューされず、
   `@coderabbitai review` の要求で処理が始まる)。**「review in progress」「Currently processing…」などの
   処理中表示が出ている間は、絶対に次へ進まない(マージしない)。**
   - CI がグリーンでも、walkthrough や「Pre-merge checks passed」だけを根拠に指摘ゼロと判断しない。
     これらは中間シグナルで、後から actionable な指摘が追加されることがある。
   - 判断が付かない場合は、次の Webhook イベントの到着を待つか、`mcp__github__pull_request_read` で
     状況を確認して進める(ユーザーへ指示を仰がない)。
   - **新しい指摘が無い差分レビューは、本文付きのレビューも通知も出さずに終わることがある。** 完了は返事の文言ではなく、
     head コミットの CodeRabbit の check run(`gh api repos/<owner>/<repo>/commits/<sha>/check-runs`)で判断する。
     要約(`output.summary`)が「Review completed」(「Review skipped」ではない)で、完了時刻(`completed_at`)が依頼より後なら、
     そのレビューは終わっている。終わっていて、最新のコミットに本文付きの CodeRabbit のレビューも未解決のスレッドも無ければ、
     「指摘無しでレビュー済み」とみなして Phase 4 へ進む。
     返事が「Review finished」に書き換わっても、指摘付きのレビューが後から付くことがあるので、それだけでは判断しない。
     もう一度 `@coderabbitai review` を送ったときの「Already reviewed the last commit」も、レビュー済みという意味で、指摘の有無は示さない。
     - 経緯:PR #174 では、指摘無しで終わった差分レビューの結果を 9 時間待ち続けた
       (head コミットの check run は、依頼の 7 分後に「Review completed」になっていた)。
       このとき最新のコミットに付いていた本文が空の CodeRabbit のレビューは、スレッドへの返信への返事で付いたもので、レビューではなかった。

3. **指摘・CI 失敗を修正する。** レビュー指摘または CI 失敗があるたびに:
   - 原因を診断してコード・記事・設定を修正する。
   - **同じ系統の穴は、指摘された 1 件だけでなくまとめて直す。** 指摘を受けたら、その関数・
     モジュール全体を読み、**同じ失敗の仕方をする経路**(入力の欠落・型違い・形式違い・
     外部取得の失敗など)を列挙し、危険側に倒れるものは同じコミットで潰す。再レビューは
     1 時間に 1 回しか回せないため、**指摘 1 件の後出しがそのまま 60 分の待機になる**。
     PR #103 では同一系統の指摘が 4 回に分かれ、3 サイクル約 3 時間を無駄にした。
   - **push 前に、Phase 1 手順 1 の独立レビューを、同じ対象・同じ止める条件で、修正後の PR の差分全体に通し、承認を記録する**
     (`article-check.mjs` → `approve.mjs start` → レビュー → `approve.mjs done`)。修正で新たに生じた食い違いを、次の再レビュー待ちの前に潰すため。
     承認が無いと pre-push フックが push を止める。
   - **「主張が計測・確認の範囲を超えている」という指摘は、主張を弱めて済ませず、まず計測して確かめられないかを考える。**
     Phase 1 手順 1 の独立レビューの指摘にも同じように当てはめる。
     - 記事なら `tools/screenshot-capture` のシーンに計測と Verifies を足して再実行し、測った条件（.NET のバージョン・OS・入力など）を併記して言い切る。
       公式ドキュメントに依る記述も、シーンで再現できるなら再現し、再現した条件を併記する。
     - 「確かめていない」「可能性がある」と書いてよいのは、原理的に測れないものだけとする。その場合も、なぜ測れないかを書く。
     - 順序や因果のように一見測れないものも、関係する参照の型や状態を測れば言い切れることがある
       (PR #170 では、参照が強いことを測って、登録が残る間はソースが回収されないと言い切った)。
     - 再レビューの待ち時間は、弱める理由にしない。技術記事は、曖昧な記載では価値が無い。
     - 経緯:PR #170(INPC の無いソースのリーク記事)では、指摘を受けるたびに「確かめていない」と書き足して収束させた。
       ユーザーから「計測すれば確実にできるのでは」と指摘され、別の型の `PropertyDescriptor` の同一性、
       登録が外れるきっかけ、参照の型、`OneTime` の更新条件などをシーンで測り直した。
   - **見送ると決めたものは、その場で理由とともにユーザーへ書く。** 黙って抱えたまま
     後から「予想していた」と言わない。指摘されたときに反論できる形で残す。
   - コミット(Phase 1 手順 2 のとおり `git add -A`)& プッシュし、必要なら CI を再実行(`mcp__github__actions_run_trigger` や再 push)する。
   - 修正の解釈に曖昧さがある場合や大規模改修が必要な場合は、`AskUserQuestion` で確認する
     (破壊的・不可逆な判断はユーザー確認を優先する)。
   - 指摘は件数を絞らない。見つけたものはすべて解消する。

4. **対応を終えたレビュースレッドは解決済みにする。**
   - **修正で対応した指摘** — 修正をコミット・プッシュしたうえで、`mcp__github__resolve_review_thread` で
     該当スレッドを解決済み(resolved)にする。
   - **反論・見送りで対応を終えた指摘**(誤検知・方針上採用しない等) — 理由を
     `mcp__github__add_reply_to_pull_request_comment` で **1 回だけ** 簡潔に返信し、
     対応方針が確定した時点でスレッドを解決済みにする。
   - スレッド ID は `mcp__github__pull_request_read`(`method: "get_review_comments"`)の各スレッドの `id` で取得する。
     修正で行が変わると `is_outdated` になるが、`is_resolved` は手動で解決するまで `false` のままである点に注意する。

5. **再レビューを依頼する。** 修正して push したら、**再レビュー依頼はレビュアーに対してのみ**行えばよい。
   ただし **MarkdownLint(`Lint Markdown` CI)も併せて再レビュー(再実行結果の確認)する**。
   - **CodeRabbit(主レビュアー)** — `.coderabbit.yaml` で `auto_incremental_review: false` としているため、
     push だけでは自動再レビューされない。PR に `@coderabbitai review` とコメントして明示的に再レビューを要求する。
     本リポジトリでは Copilot の自動レビューを使わない方針のため、構文・正確性の検証は CodeRabbit
     (`profile: assertive` + `path_instructions`)に集約している。Copilot への再レビュー要求は行わない。
   - **MarkdownLint(`Lint Markdown` CI)** — `pull_request` トリガーで push のたびに自動再実行される。
     レビュアーの再レビューと併せて、この CI の再実行結果(グリーン)も必ず確認する。
   - 再レビューで新たな指摘が来たら、手順 3〜5 を繰り返す。
   - **新たな指摘が無くなるまで**、「修正 push → 再レビュー依頼 → 対応・解決」を繰り返す
     (直近コミットに対する未解決スレッドがゼロになるまで)。

6. **マージコンフリクトを検知したら、マージのブロッカーとして解消する。** `main` が先行して
   PR が競合状態(`mcp__github__pull_request_read`(`get`)の `mergeable_state` が `dirty` 等)になったら、
   マージ不可のブロッカーとして扱い、解消するまで Phase 4 へ進まない。
   - `git fetch origin main` で最新の `main` を取得し、作業ブランチへ取り込む(`git merge origin/main`
     または `git rebase origin/main`)。
   - 競合を解消して取り込みを完了する(merge はコミット、rebase は `git rebase --continue`)。
     push の前に、Phase 1 手順 1 の「対象」の取り込みの扱いのとおりに独立レビューを通して承認を記録する(承認が無いと pre-push フックが止める)。
     そのうえで `git push`(rebase した場合は `--force-with-lease`)する。
   - push により CI は自動再実行される。必要なら CodeRabbit へ `@coderabbitai review` で再レビューを要求する。
   - 解消後は手順 1〜5 のレビュー・CI ループへ戻り、再び指摘ゼロ・グリーンを確認する。

---

## Phase 4. マージ

以下のマージ直前チェックリストを **すべて満たしてから** マージする。1 つでも満たさなければマージしない。

- [ ] 最新コミットに対する CI(`Lint Markdown` 等)が success。
      ただし `Lint Markdown`(`.github/workflows/lint-markdown.yml`)は `**/*.md` / `.markdownlint.json` /
      当該ワークフローの変更時のみ起動する。**これらを変更しない PR ではチェックが起動しない**ため、
      その場合は check run 不在(未実行)を許容し、この項目は満たされたものとして扱う。
- [ ] CodeRabbit 等の全自動レビューボットの再レビューが **完了**(処理中表示なし。CodeRabbit の完了の判定は Phase 3 手順 2 による)し、
      actionable な未解決指摘がゼロ。
- [ ] **全レビュースレッドが解決済みである。** `get_review_comments` で取得した **すべての** スレッドについて、
      作成者(CodeRabbit・人間レビュアー・その他の自動ボットを問わず)に関係なく `is_resolved == true` を要求する。
      未解決スレッドが 1 件でもあればマージしない。
- [ ] **`CHANGES_REQUESTED` のレビューが残っていない。** `get_reviews` で、dismiss されていないレビュー提出に
      `state == CHANGES_REQUESTED` が 1 件も無いことを確認する。**本文だけで紐づくスレッドが無い
      `CHANGES_REQUESTED` レビューでもマージをブロックする**(スレッド解決の確認だけでは漏れるため)。
      該当レビューは、修正のうえレビュアーに再レビューを依頼して承認/取り下げを得るか、正当な理由で dismiss されるまで解消しない。
      この条件はマージ直前の再取得後にも再検証する。
- [ ] **事前スナップショットを記録する。** マージ判定を始める前に、差分比較の基準として次を控える:
      現在の HEAD SHA、直近レビューコメントの ID、各 check run の ID と **status/conclusion**、
      各レビュースレッドの ID と **is_resolved**、
      各レビュー提出(`get_reviews`)の ID と **state**(`APPROVED` / `CHANGES_REQUESTED` / `DISMISSED` 等)。
- [ ] **マージ実行の直前に最新状態を再取得し、スナップショットと照合する。**
      `mcp__github__pull_request_read`(`get_status` / `get_check_runs` / `get_review_comments` / `get_reviews`)で再取得し、
      各対象(check run・レビュースレッド・レビュー提出)の **完全な ID セット** を突き合わせる。
      以下のいずれかが 1 件でもあれば **マージを中止してチェックリストを最初からやり直す**:
      新しい push・コミット・レビューコメント・check run の **追加または削除**、**既存 check run の status/conclusion の変化**、
      **既存レビュースレッドの追加・削除・is_resolved の変化**、
      **既存レビュー提出の追加・削除・state の変化**(`APPROVED` / `CHANGES_REQUESTED` / dismissal。新規コメントや check run を
      伴わず、同じ ID のまま state だけが変わる場合や、スナップショットにあった項目が消えた場合も含む)。
      差分が無い場合のみ次へ進む(TOCTOU 回避)。
- [ ] **サーバー側ガードが無い場合は自動マージしない。** `main` にブランチ保護(必須ステータスチェック・
      Require branches to be up to date)が構成されておらず、厳密な保証が必要な場合は、
      `merge_pull_request` を呼ばずに中止してユーザーへ報告し、判断を仰ぐ。

> **マージ認可について:** 本スキルは `article-workflow` と同様、上記チェックリストをすべて満たしたら
> **マージ直前の追加確認なしで自動マージする** 設計である。スキルの起動そのものがマージの認可にあたる
> (ユーザーがこのワークフローの実行を指示した時点で、チェックリスト充足後のマージまでを許可している)。
> ただしチェックリストの各項目(特に「サーバー側ガードが無い場合は自動マージしない」)や、
> 修正方針に重大な曖昧さがある場合の `AskUserQuestion` は引き続き適用され、無条件の autonomy ではない。

チェックリストを満たしたら:

1. **マージする。** `mcp__github__merge_pull_request` で PR を `main` にマージする。
2. **マージ成功を確認する。** 応答の `merged: true` とマージコミット SHA を確認し、続けて
   `mcp__github__pull_request_read`(`get`)で PR 状態が `MERGED`、かつマージ済み head が事前スナップショットの
   HEAD SHA と一致することを確認する。想定と異なる head がマージされていたら続行せずユーザーへ報告する。
3. **リモートブランチ削除は GitHub の自動削除に任せる(手動削除コマンドは実行しない)。**
   本リポジトリは「Automatically delete head branches」が有効なため、マージすると head ブランチは自動削除される。
   > ⚠️ Web 実行環境ではリモートブランチの手動削除はできない(`git push origin --delete` も REST API も 403 で失敗する)。試みない。
4. **ローカルの作業ブランチ**は不要なら削除してよい(`git branch -d "<branch>"`。ブランチ名はクォートして渡す)。
5. **購読を解除する。** `unsubscribe_pr_activity` で PR の監視を終了する。
6. 完了をユーザーへ日本語で報告する(PR 番号・マージ済みである旨)。

## 全体フロー要約

```text
Phase 1  setup・機械チェック・過去指摘の集計・approve start → 3 観点の独立レビュー(要修正ゼロまで)→ approve done
         → コミット → プッシュ(pre-push フックが承認と照合)
         (「対象」の例外: setup → article-check → approve direct → コミット → プッシュ)
Phase 2  PR 作成 → subscribe_pr_activity で購読
Phase 3  レビュー待ち(Webhook)→ 指摘修正 → 独立レビュー・approve done → push(pre-push フックが照合)→ 再レビュー依頼
           ── 指摘ゼロまでループ
           (修正 push 後は CodeRabbit へ `@coderabbitai review` で再レビューを要求し、MarkdownLint も併せて再確認、
            対応済みスレッドは解決済みにする)
Phase 4  マージ直前チェックリスト → マージ →(head ブランチは GitHub が自動削除)→ 購読解除 → 完了報告
```

## 判断の原則

- **(CodeRabbit など PR 上の)レビュー指摘は件数を絞らない。** 見つけたものはすべて解消する。
- **同じ系統の穴はまとめて直す。** 再レビューは 1 時間に 1 回しか回せないので、
  指摘 1 件の後出しは 60 分の待機を自分で作ることになる。見送るなら黙らずに理由を書く。
- **push の前に独立レビューを通し、承認を記録する**(対象と例外は Phase 1 手順 1 の「対象」による)。
  push は pre-push フックが承認と照合する。フックを外したり `--no-verify` を付けたりしない。
- **`sleep` でポーリングせず、`send_later` での予約もしない。** レビュー・CI の結果は Webhook イベントで
  届くので、届くものは到着を待つ。CI 成功・新規 push・マージコンフリクトの遷移など **Webhook で届かない
  イベント** は、購読直後の再取得(Phase 2 手順 4)や、長時間反応が無い場合の `mcp__github__pull_request_read`
  での状況確認で補う(ユーザーへ指示を仰がず自分で確認して進める)。
- **対応を終えたレビュー指摘はスレッドを解決済みにする。** マージ前に未解決スレッドを残さない。
- **処理中の自動レビューボットがある間はマージしない。** 中間シグナルでマージ判断をしない。
- **リモートブランチの手動削除コマンドは実行しない**(Web 環境では 403 で必ず失敗する)。head ブランチの削除は自動削除に任せる。
- 修正方針に重大な曖昧さがある場合や不可逆操作の前は `AskUserQuestion` でユーザーに確認する。
