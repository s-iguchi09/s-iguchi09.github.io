# PR 作成・レビュー対応・マージ ワークフロー

作業ブランチ上の変更に対して **PR 作成 → レビュー待ち → 指摘修正 → 再レビュー依頼(ループ)→ マージ** を実行するスキル。
記事作成は含まない。既にコミット済み(または本セッションでコミットできる)変更があり、それを PR にして公開まで持っていく場面で使う。

> **言語ルール:** ユーザーへの発信(質問・進捗報告・PR 説明文・コミットメッセージなど)はすべて **日本語** で行う(`CLAUDE.md`)。
>
> **参考:** レビュー対応・マージの手順は `article-workflow` スキルの Phase 4・5 に準拠する。
> 本スキルはその PR 以降の部分を単体で実行するためのもの。

---

## Phase 1. コミット & プッシュ

1. **push の前に(可能ならコミットの前に)、文脈を持たないサブエージェントで独立レビューする。**
   CodeRabbit の再レビューには回数制限がある(Phase 3 手順 3)ため、push 前に拾える指摘は先に潰す。
   書いた本人は意図を知っているぶん食い違いを見落とすので、会話の文脈を引き継がないサブエージェントに見せる。
   - **対象:** push するすべての差分に行う。例外は、`article-workflow` の Phase 2(手順 5 の `/code-review high` まで)が
     収束したあと、1 行も変更していない差分を push する場合だけとする(`article-workflow` の Phase 3 の「修正あり」で Phase 2 に戻り、収束し直した場合も含む)。
     `article-workflow` の Phase 2 のあとに CI の修正・PR 上のレビュー指摘への対応などで直した場合は、記事だけの変更でも、
     直した後の差分に行う。`/code-review high` の再実行はこの独立レビューの代わりにしない。
     この条件は `article-workflow` からも参照する。
   - **起動する前に、作業の写しをリポジトリの外に置く。** 作業ツリーはそのまま残し、写しだけを外に作る。
     原因は特定できていないが、一時コピーの削除が失敗した直後に元のリポジトリが `.git` ごと空になった例があり(経緯を参照)、
     そのとき作業を戻せたのは外に写しがあったからである。未 push のコミットや `git stash` は `.git` の中にあるため、写しに数えない。
     `<外のパス>` は、一時コピーの置き場(下の手順の `<一時パス>`)とは別の場所に、回ごとに一意の名前で作る
     (例: `<スクラッチ>/backup-20261101-080512/`)。既にあるディレクトリを使い回さず、`mkdir`(`-p` を付けない)で新しく作り、
     作れなかったら別の名前にする。次の手順はどれか 1 つでも失敗したら、`Agent` を起動せずに止めて、ユーザーに報告する。
     - 未 push のコミット: `git fetch origin main` のあと、`git rev-list --count origin/main..HEAD` が 1 以上なら
       `git bundle create <外のパス>/work.bundle origin/main..HEAD` で書き出し、`git bundle verify <外のパス>/work.bundle` が通ることを確かめる(0 なら省く)
     - 未コミットの変更: `git diff --binary HEAD > <外のパス>/work.patch`(変更が無ければ省く)
     - 未追跡ファイル: `git ls-files --others --exclude-standard -z` の一覧(NUL 区切り)にあるものを外へコピーする
   - `Agent` ツールで、文脈を引き継がない種別(`general-purpose` など。fork は使わない)を起動し、次だけを渡す。
     - 対象リポジトリのパス・ブランチと、差分の取り方(`git fetch origin main` のあと
       `git diff --ignore-cr-at-eol origin/main`。未コミットの変更を含める)と、
       未追跡の新規ファイルの一覧(`git status --short --untracked-files=all`)。新規ファイルは `git diff` に出ないため、一覧を渡して読ませる
     - **レビュー範囲は PR の差分全体とすること。** 指摘への修正を push する前でも、直した箇所だけに絞らない。
       直した箇所を重点的に見てほしいときは、範囲を狭めずに「特に見てほしい箇所」として添える
     - `.coderabbit.yaml` の `path_instructions` を読み、同じ基準で見ること
     - CodeRabbit がレビュー基準として自動で読むガイドラインを読み、同じ基準で見ること。
       リポジトリルートと変更ファイルの上位ディレクトリにある `CLAUDE.md` / `AGENTS.md`、
       および存在すれば `.claude/rules/**/*.md`
     - 変更ファイルが参照している規約と、変更箇所を参照している側も読むこと
     - (あれば)依頼者が元の作業ツリーで実行したコマンドと、その終了コード・生成物。あわせて、実行したときの HEAD のコミットと、
       未コミット・未追跡の変更が実行の後に変わっていないこと(実行後に変更していなければ、そう明記する)、実行した環境(OS・SDK・ツールのバージョン)
     - **差分で追加・変更した手順・チェックリスト・スクリプトのヘッダーコメントにあるコマンドは、書かれた場所から
       書かれた順に実行して確かめること。** 変更していない前段(`cd` や前提のインストールなど)も含めて手順の頭から実行し、
       前のコマンドで移った作業ディレクトリを引き継いで、パスが解決できるか、終了コードが書かれたとおりになるかを見る。
       説明のための例示コマンドは対象外
       - **元の作業ツリーでは、コミット・ステージ・ファイルの変更をせず、作業ツリーを書き換えるコマンド(生成・整形・`npm ci` など)も
         実行しない。** そうしたコマンドは、次の順で選ぶ。
         1. 書かれたコマンドと同じことを、書き換えずに確かめられるなら、それで済ませる。`--check` のような検査用の引数があれば使う。
            依頼者が元の作業ツリーで実行した結果を渡されていて、そのときの HEAD と未コミット・未追跡の変更がレビュー対象と同じで、
            実行した環境(OS・SDK・ツールのバージョン)が、確かめる対象の手順が前提とする環境と同じなら、実行し直さずにそれを使う。
            環境が分からないときは使わず、2 に進むか「未実行(推論)」として扱う。
            書き換えずには確かめられない部分(たとえば `npm ci && node generate.mjs --check` の `npm ci`)は、2 に進む
         2. それでも実行が要るときだけ、`git worktree add --detach <一時パス> HEAD` で一時コピーを作って実行する。
            `<一時パス>` は、リポジトリの外の、ドライブやルートの直下から 2 階層以内の短いパスに置き、名前は毎回一意にする
            (例: Windows では `D:\wt\r-20261101-080512`、それ以外では `/tmp/wt-r-20261101-080512`)。
            `add` の前にそのパスが無いことを確かめ、あれば別の名前にする。スクラッチのディレクトリのような長いパスには置かない
            (長いパスの対応が無効な Windows の環境では、パスが MAX_PATH(260 文字)を超えると、dotnet のビルドや Git の削除が失敗することがある。
            PR #170 では、ビルドが MSB3030 で、`git worktree remove --force` が `Filename too long` で失敗した)。
            作れたら、`git worktree list --porcelain` に表示されたその一時コピーのパスを、後始末のために控えておく。
            未コミット・未追跡の変更は一時コピーに入らないため、追跡ファイルの変更は元の作業ツリーで
            `git diff --binary HEAD | git -C <一時パス> apply` を実行して写し、未追跡ファイルは元の作業ツリーで
            `git ls-files --others --exclude-standard -z` の一覧(NUL 区切り)にあるものを一時コピーへコピーする。
            リポジトリの外に書き込めない(権限の確認やサンドボックスで拒否される)ときは、一時コピーを作らず、下の「未実行(推論)」として扱う
       - 一時コピーを作れた場合は、コマンドが失敗した場合や変更が残った場合も含めて、最後に必ず
         `git worktree remove --force <一時パス>` で消す(変更が残った worktree は `--force` なしでは消えない)。
         消す対象は、この回に自分で作った一時パスだけとする。消す前に `git worktree list --porcelain` を実行し、
         作ったときに控えたパスと同じ worktree が載っていることを確かめる。載っていない、または別のパスしか無いときは消さずに報告する
       - **`git worktree remove --force` が失敗したら(`Filename too long` など)、それ以上消そうとしない。**
         削除コマンドの再試行や `rm -rf` をせず、まず元の作業ツリーが無事か(`git -C <元のパス> status` が通り、
         ファイルが揃っているか)を確かめる。そのうえで、一時パスが残っていることと合わせて依頼者に報告する。
         報告を受けた依頼者も、`git worktree remove --force` をやり直さず、一時パスを自分で消さない。
         残った一時パスはユーザーに伝えて手で消してもらい、消し終えたと返事を受けてから、依頼者が元のリポジトリで
         `git worktree prune` を実行し、`git worktree list` に残っていないことを確かめる
       - 外部への書き込みは実行しない。push・PR やコメントの投稿・マージ・外部サービスへの送信が該当する。
         パッケージの取得など読み取りだけの通信は、確かめる対象の手順に書かれている場合に限り実行してよい
       - 実行できなかったコマンドは、手順を読んで推論でたどり、指摘に「未実行(推論)」と書き添える
     - 上の実行を除き、読むだけでファイルを変更しないこと
     - 指摘は件数を絞らず、各指摘に「ファイル:行」「何が問題か」「直し方」「重要度(要修正 / 軽微 / 見送り可)」を付けること
   - 少なくとも次の観点を確認させる。
     - **同じ規則を書いた箇所どうしが一致しているか。** 語・項目・条件・例外が食い違っていないか。
       変更した規則を、変更していないファイルが古い定義のまま書いていないか(規則のキーワードで全体を `grep` させる)。
       同じ規則を複数の場所に書き写していないか(書き写すと、片方を直したときにずれる。規則は 1 か所に書き、他からは参照する)
     - **番号と参照。** 節番号・手順番号の並びと、それを参照している箇所が合っているか
     - **主張と根拠の強さ。** 「仮説」「未検証」とした内容を、別の文で断定していないか
     - **基準が具体的か。** 期間・閾値・対象が日付・数値・パスで特定できるか。期間どうしが矛盾していないか
     - **PR 自身が足した規則に、PR 内の変更が従っているか**
     - **字数・件数の上限。** レビュアー自身がスクリプトで測って確かめる
     - **体裁。** markdownlint(`.markdownlint.json`)に通るか。記事を含む場合は `docs/rules/article/guidelines.md` §9 の改行規則にも従うか
   - **止める条件:** 要修正はすべて直し、修正後の PR の差分全体を同じ条件で再びレビューさせる。要修正が無くなるまで繰り返す。
     軽微・見送り可は、直すか、見送る理由を残す。PR を作る前なら、PR 作成時に PR 説明へ書く
     (このスキルの Phase 2 手順 2 / `article-workflow` の Phase 4 手順 2)。
     PR が既にある場合(PR 作成後の修正 push など)は、PR へのコメントか PR 説明の更新で残す。
     どちらの場合もユーザーへ報告する。判断の原則の「指摘は件数を絞らない」は PR 上のレビュー指摘についてのもので、
     この独立レビューには適用しない(assertive に広く挙げさせるため、軽微なものまで直すと収束しないことがある)。
   - **CodeRabbit の代わりではない。** マージの条件は引き続き Phase 4 のマージ直前チェックリストとする。
   - 経緯:PR #165(既存記事の `seo_title` 修正と、タイトルのレビュー観点の規約への追加)は、この手順を入れずに push した。
     CodeRabbit が規約どうしの表記ゆれや曖昧な期間指定を 1 回に 1〜5 件ずつ指摘し、再レビューのたびに 1 時間待った。
     途中でこの手順を試したところ、同じ種類の指摘が 1 回でまとめて見つかった。
     PR #168(OGP 画像)では push のたびにこの手順を通したが、指摘への修正の push 前に直した箇所だけを見させ、
     コマンドも実行させていなかった。CodeRabbit は差分全体から 3 件、次の回にも 1 件
     (チェックリストのコマンドを書かれた順に打つと存在しないパスを探す)を指摘し、そのたびに 1 時間待った。
     範囲を差分全体に固定することと、コマンドを書かれた順に実行させることは、これを受けて足した。
     一時コピーの作り方・後始末・書き込みの禁止範囲は、この追加の PR(#169)への CodeRabbit の指摘を受けて足した。
     PR #170 では、一時コピーをスクラッチの長いパスに作ったところ、ビルドが MAX_PATH を超えて失敗した。続く
     `git worktree remove --force` も `Filename too long` で失敗し、その直後に元のリポジトリが `.git` ごと空になった
     (リポジトリの外に写してあった作業を、clone し直したリポジトリへ戻して復旧した)。書き換えずに確かめる方法を先に選ぶこと、
     一時コピーを短いパスに一意の名前で置くこと、起動前に作業の写しをリポジトリの外に置くこと、削除に失敗したら元の作業ツリーを先に確かめることは、これを受けて足した。

2. **変更をコミットする。** 手順 1 で直した分を含め、未コミットの変更があればコミットする。
   追加の変更が無い場合はコミットを省略する(`nothing to commit` で止めない)。

3. **プッシュする。** `git push -u origin "<branch>"` で作業ブランチへ push する。
   - ブランチ名は必ずクォートして渡す(シェルのメタ文字によるコマンドインジェクションを防ぐ)。
   - ネットワークエラー時は 2s/4s/8s/16s の指数バックオフで最大 4 回リトライする。
   - **push に成功してから Phase 2 へ進む。** 4 回の再試行をすべて失敗した場合、またはネットワーク以外の
     エラー(認証・権限・非 fast-forward 等)が発生した場合は Phase 2 へ進まず、処理を中止してユーザーへ報告する。
     リモートに最新コミットが無いまま古い内容で PR を作成・再利用しないためのガードである。
   - 未 push のコミットが残っていれば push してから Phase 2 へ進む。

## Phase 2. PR 作成

1. **既存の PR を確認する(重複作成の防止)。** PR 作成前に、現在のブランチから `main` 宛ての
   オープンな PR が既に存在しないかを `mcp__github__list_pull_requests`(`head` にブランチ、`base` に `main` を指定)で検索する。
   - **ベースが `main` の PR だけを対象にする。** `head` だけで絞ると、同じブランチから別ベース向けに
     作られた PR を誤って再利用しかねない。`base` でも絞るか、返却結果の `base.ref == "main"` を必ず確認する。
   - **既にオープンな `main` 宛て PR があれば、それを再利用する。** `create_pull_request` は再実行せず、その PR 番号で
     手順 3(購読)へ進む。Phase 3 のフォールバックからセッションを再開した場合など、重複した PR や
     購読を作らないためのガードである。
   - 該当するオープンな PR が無い場合のみ、手順 2 で新規作成する。

2. **PR を作成する。** GitHub MCP(`mcp__github__create_pull_request`)で `main` 宛の PR を作成する。
   - リポジトリに PR テンプレート(`.github/pull_request_template.md` 等)があれば、その見出し構成に沿って本文を埋める。
   - タイトル・本文は日本語で記述する。変更内容を要約し、テンプレートの各節を埋める。

3. **PR を購読する。** `subscribe_pr_activity` で PR を購読し、以降のイベント
   (CI 結果・レビューコメント)を `<github-webhook-activity>` として受け取れるようにする。

4. **購読直後に PR 状態を再取得して同期する。** PR 作成から購読までの間に CI や自動レビューが
   始まる/完了することがあり、その分の Webhook を取りこぼす可能性がある。購読直後に
   `mcp__github__pull_request_read`(`get_status` / `get_check_runs` / `get_review_comments`)で
   状態を再取得し、既に発生済みの CI 結果・レビュー指摘を Phase 3 に持ち込む。

## Phase 3. レビュー待ち → 指摘修正 → 再レビュー依頼(指摘ゼロまでループ)

**指摘が無くなるまで**、以下 1〜5 を繰り返す。

1. **レビューの Webhook 通知を待つ。** PR 作成後、CodeRabbit 等の自動レビューが始まる。
   - **`sleep` でのポーリングはしない。** レビューコメントや CI 結果は
     `<github-webhook-activity>` イベントとしてこのセッションに届く。イベントの到着を待つ。
   - **`send_later` でのセルフチェックイン予約は行わない。** CI 成功・新規 push・マージコンフリクトの
     遷移は Webhook で届かないことがあるが、`sleep` ポーリングも `send_later` 予約もしない。
     長時間反応が無い場合はユーザーへ指示を仰がず、`mcp__github__pull_request_read`
     (`get_status` / `get_check_runs` / `get_review_comments`)で状況を確認し、Phase 3 を続行する。

2. **自動レビューボットの完了を必ず待つ。** `coderabbitai` などはレビュー要求後に処理が走り、
   完了まで数分かかる(CodeRabbit は `auto_incremental_review: false` のため push だけでは再レビューされず、
   `@coderabbitai review` の要求で処理が始まる)。**「review in progress」「Currently processing…」などの
   処理中表示が出ている間は、絶対に次へ進まない(マージしない)。**
   - CI がグリーンでも、walkthrough や「Pre-merge checks passed」だけを根拠に指摘ゼロと判断しない。
     これらは中間シグナルで、後から actionable な指摘が追加されることがある。
   - 判断が付かない場合は、次の Webhook イベントの到着を待つか、`mcp__github__pull_request_read` で
     状況を確認して進める(ユーザーへ指示を仰がない)。

3. **指摘・CI 失敗を修正する。** レビュー指摘または CI 失敗があるたびに:
   - 原因を診断してコード・記事・設定を修正する。
   - **同じ系統の穴は、指摘された 1 件だけでなくまとめて直す。** 指摘を受けたら、その関数・
     モジュール全体を読み、**同じ失敗の仕方をする経路**(入力の欠落・型違い・形式違い・
     外部取得の失敗など)を列挙し、危険側に倒れるものは同じコミットで潰す。再レビューは
     1 時間に 1 回しか回せないため、**指摘 1 件の後出しがそのまま 60 分の待機になる**。
     PR #103 では同一系統の指摘が 4 回に分かれ、3 サイクル約 3 時間を無駄にした。
   - **push 前に、Phase 1 手順 1 の独立レビューを、同じ対象・同じ止める条件で、修正後の PR の差分全体に通す。**
     修正で新たに生じた食い違いを、次の再レビュー待ちの前に潰すため。
   - **「主張が計測・確認の範囲を超えている」という指摘は、主張を弱めて済ませず、まず計測して確かめられないかを考える。**
     Phase 1 手順 1 の独立レビューの指摘にも同じように当てはめる。
     - 記事なら `tools/screenshot-capture` のシーンに計測と Verifies を足して再実行し、測った条件（.NET のバージョン・OS・入力など）を併記して言い切る。
       公式ドキュメントに依る記述も、シーンで再現できるなら再現し、再現した条件を併記する。
     - 「確かめていない」「可能性がある」と書いてよいのは、原理的に測れないものだけとする。その場合も、なぜ測れないかを書く。
     - 順序や因果のように一見測れないものも、関係する参照の型や状態を測れば言い切れることがある
       (PR #170 では、参照が強いことを測って、登録が残る間はソースが回収されないと言い切った)。
     - 再レビューの待ち時間は、弱める理由にしない。技術記事は、曖昧な記載では価値が無い。
     - 経緯:PR #170(INPC の無いソースのリーク記事)では、指摘を受けるたびに「確かめていない」と書き足して収束させた。
       ユーザーから「計測すれば確実にできるのでは」と指摘され、別の型の `PropertyDescriptor` の同一性、
       登録が外れるきっかけ、参照の型、`OneTime` の更新条件などをシーンで測り直した。
   - **見送ると決めたものは、その場で理由とともにユーザーへ書く。** 黙って抱えたまま
     後から「予想していた」と言わない。指摘されたときに反論できる形で残す。
   - コミット & プッシュし、必要なら CI を再実行(`mcp__github__actions_run_trigger` や再 push)する。
   - 修正の解釈に曖昧さがある場合や大規模改修が必要な場合は、`AskUserQuestion` で確認する
     (破壊的・不可逆な判断はユーザー確認を優先する)。
   - 指摘は件数を絞らない。見つけたものはすべて解消する。

4. **対応を終えたレビュースレッドは解決済みにする。**
   - **修正で対応した指摘** — 修正をコミット・プッシュしたうえで、`mcp__github__resolve_review_thread` で
     該当スレッドを解決済み(resolved)にする。
   - **反論・見送りで対応を終えた指摘**(誤検知・方針上採用しない等) — 理由を
     `mcp__github__add_reply_to_pull_request_comment` で **1 回だけ** 簡潔に返信し、
     対応方針が確定した時点でスレッドを解決済みにする。
   - スレッド ID は `mcp__github__pull_request_read`(`method: "get_review_comments"`)の各スレッドの `id` で取得する。
     修正で行が変わると `is_outdated` になるが、`is_resolved` は手動で解決するまで `false` のままである点に注意する。

5. **再レビューを依頼する。** 修正して push したら、**再レビュー依頼はレビュアーに対してのみ**行えばよい。
   ただし **MarkdownLint(`Lint Markdown` CI)も併せて再レビュー(再実行結果の確認)する**。
   - **CodeRabbit(主レビュアー)** — `.coderabbit.yaml` で `auto_incremental_review: false` としているため、
     push だけでは自動再レビューされない。PR に `@coderabbitai review` とコメントして明示的に再レビューを要求する。
     本リポジトリでは Copilot の自動レビューを使わない方針のため、構文・正確性の検証は CodeRabbit
     (`profile: assertive` + `path_instructions`)に集約している。Copilot への再レビュー要求は行わない。
   - **MarkdownLint(`Lint Markdown` CI)** — `pull_request` トリガーで push のたびに自動再実行される。
     レビュアーの再レビューと併せて、この CI の再実行結果(グリーン)も必ず確認する。
   - 再レビューで新たな指摘が来たら、手順 3〜5 を繰り返す。
   - **新たな指摘が無くなるまで**、「修正 push → 再レビュー依頼 → 対応・解決」を繰り返す
     (直近コミットに対する未解決スレッドがゼロになるまで)。

6. **マージコンフリクトを検知したら、マージのブロッカーとして解消する。** `main` が先行して
   PR が競合状態(`mcp__github__pull_request_read`(`get`)の `mergeable_state` が `dirty` 等)になったら、
   マージ不可のブロッカーとして扱い、解消するまで Phase 4 へ進まない。
   - `git fetch origin main` で最新の `main` を取得し、作業ブランチへ取り込む(`git merge origin/main`
     または `git rebase origin/main`)。
   - 競合を解消してコミットし、`git push`(rebase した場合は `--force-with-lease`)する。
   - push により CI は自動再実行される。必要なら CodeRabbit へ `@coderabbitai review` で再レビューを要求する。
   - 解消後は手順 1〜5 のレビュー・CI ループへ戻り、再び指摘ゼロ・グリーンを確認する。

## Phase 4. マージ

以下のマージ直前チェックリストを **すべて満たしてから** マージする。1 つでも満たさなければマージしない。

- [ ] 最新コミットに対する CI(`Lint Markdown` 等)が success。
      ただし `Lint Markdown`(`.github/workflows/lint-markdown.yml`)は `**/*.md` / `.markdownlint.json` /
      当該ワークフローの変更時のみ起動する。**これらを変更しない PR ではチェックが起動しない**ため、
      その場合は check run 不在(未実行)を許容し、この項目は満たされたものとして扱う。
- [ ] CodeRabbit 等の全自動レビューボットの再レビューが **完了**(処理中表示なし)し、actionable な未解決指摘がゼロ。
- [ ] **全レビュースレッドが解決済みである。** `get_review_comments` で取得した **すべての** スレッドについて、
      作成者(CodeRabbit・人間レビュアー・その他の自動ボットを問わず)に関係なく `is_resolved == true` を要求する。
      未解決スレッドが 1 件でもあればマージしない。
- [ ] **`CHANGES_REQUESTED` のレビューが残っていない。** `get_reviews` で、dismiss されていないレビュー提出に
      `state == CHANGES_REQUESTED` が 1 件も無いことを確認する。**本文だけで紐づくスレッドが無い
      `CHANGES_REQUESTED` レビューでもマージをブロックする**(スレッド解決の確認だけでは漏れるため)。
      該当レビューは、修正のうえレビュアーに再レビューを依頼して承認/取り下げを得るか、正当な理由で dismiss されるまで解消しない。
      この条件はマージ直前の再取得後にも再検証する。
- [ ] **事前スナップショットを記録する。** マージ判定を始める前に、差分比較の基準として次を控える:
      現在の HEAD SHA、直近レビューコメントの ID、各 check run の ID と **status/conclusion**、
      各レビュースレッドの ID と **is_resolved**、
      各レビュー提出(`get_reviews`)の ID と **state**(`APPROVED` / `CHANGES_REQUESTED` / `DISMISSED` 等)。
- [ ] **マージ実行の直前に最新状態を再取得し、スナップショットと照合する。**
      `mcp__github__pull_request_read`(`get_status` / `get_check_runs` / `get_review_comments` / `get_reviews`)で再取得し、
      各対象(check run・レビュースレッド・レビュー提出)の **完全な ID セット** を突き合わせる。
      以下のいずれかが 1 件でもあれば **マージを中止してチェックリストを最初からやり直す**:
      新しい push・コミット・レビューコメント・check run の **追加または削除**、**既存 check run の status/conclusion の変化**、
      **既存レビュースレッドの追加・削除・is_resolved の変化**、
      **既存レビュー提出の追加・削除・state の変化**(`APPROVED` / `CHANGES_REQUESTED` / dismissal。新規コメントや check run を
      伴わず、同じ ID のまま state だけが変わる場合や、スナップショットにあった項目が消えた場合も含む)。
      差分が無い場合のみ次へ進む(TOCTOU 回避)。
- [ ] **サーバー側ガードが無い場合は自動マージしない。** `main` にブランチ保護(必須ステータスチェック・
      Require branches to be up to date)が構成されておらず、厳密な保証が必要な場合は、
      `merge_pull_request` を呼ばずに中止してユーザーへ報告し、判断を仰ぐ。

> **マージ認可について:** 本スキルは `article-workflow` と同様、上記チェックリストをすべて満たしたら
> **マージ直前の追加確認なしで自動マージする** 設計である。スキルの起動そのものがマージの認可にあたる
> (ユーザーがこのワークフローの実行を指示した時点で、チェックリスト充足後のマージまでを許可している)。
> ただしチェックリストの各項目(特に「サーバー側ガードが無い場合は自動マージしない」)や、
> 修正方針に重大な曖昧さがある場合の `AskUserQuestion` は引き続き適用され、無条件の autonomy ではない。

チェックリストを満たしたら:

1. **マージする。** `mcp__github__merge_pull_request` で PR を `main` にマージする。
2. **マージ成功を確認する。** 応答の `merged: true` とマージコミット SHA を確認し、続けて
   `mcp__github__pull_request_read`(`get`)で PR 状態が `MERGED`、かつマージ済み head が事前スナップショットの
   HEAD SHA と一致することを確認する。想定と異なる head がマージされていたら続行せずユーザーへ報告する。
3. **リモートブランチ削除は GitHub の自動削除に任せる(手動削除コマンドは実行しない)。**
   本リポジトリは「Automatically delete head branches」が有効なため、マージすると head ブランチは自動削除される。
   > ⚠️ Web 実行環境ではリモートブランチの手動削除はできない(`git push origin --delete` も REST API も 403 で失敗する)。試みない。
4. **ローカルの作業ブランチ**は不要なら削除してよい(`git branch -d "<branch>"`。ブランチ名はクォートして渡す)。
5. **購読を解除する。** `unsubscribe_pr_activity` で PR の監視を終了する。
6. 完了をユーザーへ日本語で報告する(PR 番号・マージ済みである旨)。

## 全体フロー要約

```text
Phase 1  文脈なしサブエージェントで独立レビュー(要修正ゼロまで)→ コミット → プッシュ
Phase 2  PR 作成 → subscribe_pr_activity で購読
Phase 3  レビュー待ち(Webhook)→ 指摘修正 → 独立レビュー → 再レビュー依頼  ── 指摘ゼロまでループ
           (修正 push 後は CodeRabbit へ `@coderabbitai review` で再レビューを要求し、MarkdownLint も併せて再確認、
            対応済みスレッドは解決済みにする)
Phase 4  マージ直前チェックリスト → マージ →(head ブランチは GitHub が自動削除)→ 購読解除 → 完了報告
```

## 判断の原則

- **(CodeRabbit など PR 上の)レビュー指摘は件数を絞らない。** 見つけたものはすべて解消する。
- **同じ系統の穴はまとめて直す。** 再レビューは 1 時間に 1 回しか回せないので、
  指摘 1 件の後出しは 60 分の待機を自分で作ることになる。見送るなら黙らずに理由を書く。
- **push の前に独立レビューを通す**(対象と例外は Phase 1 手順 1 の「対象」による)。
- **`sleep` でポーリングせず、`send_later` での予約もしない。** レビュー・CI の結果は Webhook イベントで
  届くので、届くものは到着を待つ。CI 成功・新規 push・マージコンフリクトの遷移など **Webhook で届かない
  イベント** は、購読直後の再取得(Phase 2 手順 4)や、長時間反応が無い場合の `mcp__github__pull_request_read`
  での状況確認で補う(ユーザーへ指示を仰がず自分で確認して進める)。
- **対応を終えたレビュー指摘はスレッドを解決済みにする。** マージ前に未解決スレッドを残さない。
- **処理中の自動レビューボットがある間はマージしない。** 中間シグナルでマージ判断をしない。
- **リモートブランチの手動削除コマンドは実行しない**(Web 環境では 403 で必ず失敗する)。head ブランチの削除は自動削除に任せる。
- 修正方針に重大な曖昧さがある場合や不可逆操作の前は `AskUserQuestion` でユーザーに確認する。
