# 記事レビューチェックリスト

技術記事の公開前にこのチェックリストを使用すること。

---

## 構成

まず記事タイプを確認する（`guidelines.md` §2）。

- [ ] 記事タイプを選択した：□ 問題解決型（§2.1） / □ 手順・解説型（§2.2）

**両タイプ共通（必須）:**

- [ ] タイトルが技術テーマを明確に示している
- [ ] 概要セクションに記事が扱う内容が記述されている（問題解決型では解決する問題、手順・解説型では既定の挙動やカスタマイズが必要な理由も明示）
- [ ] 前提・対象環境セクションにフレームワーク、バージョン、アーキテクチャが記述されている
- [ ] コードを伴う記事で、説明付きの実装例が含まれている
- [ ] 注意点（制約・エッジケース・落とし穴）が独立セクションまたは各手法の補足として少なくとも1つ記述されている
- [ ] まとめセクションに選択基準を含む具体的な推奨が記述されている

**問題解決型（§2.1）のみ:**

- [ ] 問題セクションに状況が具体的に記述されている
- [ ] 原因・背景セクションに問題が起きる理由が説明されている
- [ ] 解決方法セクションに推奨アプローチが説明されている
- [ ] 代替案・比較セクションに他の選択肢とトレードオフが記述されている

**手順・解説型（§2.2）のみ:**

- [ ] 本文がアプローチ別の見出しで構成され、各手法に実装例がある
- [ ] まとめに比較表が含まれている（推奨）

---

## コードとコンテンツ

- [ ] すべてのコードブロックに前後の説明文がある
- [ ] コードが大部分を占め説明文が最小限の状態になっていない
- [ ] 選択基準（どの状況でどのアプローチを使うか）が明示されている
- [ ] ソリューションの制限事項が記述されている
- [ ] 比較表・落とし穴・実用的なガイダンスのうち少なくとも1つが含まれている

---

## 文体

- [ ] Q&A形式の見出しがない（例: "対応できるか？" → "対応方法"）
- [ ] 会話的な書き出しがない（例: "はい、対応できます" / "Let's try…"）
- [ ] 接続詞の埋め草がない（例: "結論としては" / "つまり" / "As you can see"）
- [ ] 文体が断定的・無主語構文になっている
- [ ] 記事が1つのテーマのみを扱っている
- [ ] 文末ごとに改行が入っている（読点・カンマでは改行していない）

---

## 図・スクリーンショット（`guidelines.md` §11）

- [ ] 記事の内容を補う図またはスクリーンショットが少なくとも1点含まれている
- [ ] 実行結果が画面に現れるテーマでは、モックアップではなく実際に動かしたスクリーンショットを使っている
- [ ] 図が示す挙動を実際に動かして確認し、本文の記述と一致している
- [ ] 図が、直前に載せたコードから再現できる内容になっている（図にしか出てこない要素・設定が無い）
- [ ] 実測値を載せている場合、結果を左右する条件（テーマ・`ControlTemplate`・入力データなど）をキャプションに書いている
- [ ] 主張が再現しなかった記事は、図を省略せず本文を修正している（§11.2）
- [ ] 画像が `images/articles/<slug>/` に置かれ、本文から `/images/...` のサイト絶対パスで参照されている
- [ ] `figure class="article-figure"` で囲み、`figcaption` に説明（生成した環境を含む）を書いている
- [ ] `alt` が設定され、内容を説明する文になっている
- [ ] `width` / `height` に実際のピクセル寸法を、`loading="lazy"` を指定している
- [ ] 図の前後に空行がある（`hard_wrap: true` のため、無いと直前の文と連結される）
- [ ] 本文幅より広い図に `article-figure--wide` を付けている
- [ ] 日英で同じ画像を共有し、`alt` と `figcaption` のみ各言語で書いている
- [ ] 全記事で同じ種類の図を同じ位置に機械的に入れていない（§10）

---

## 主張の検証（`guidelines.md` §12）

- [ ] 記事の主張を `tools/screenshot-capture` のシーンとして実装し、実行して確認した
- [ ] シーンを記事と同じ PR に含めており、`dotnet run --project tools/screenshot-capture -c Release -- <slug>` で再現できる
- [ ] 生成した画像を目視で確認した（中身が白紙になっていない）
- [ ] 動かして確認できなかった主張を、削るか確認していない旨を明記した（未検証の断定を残していない）
- [ ] 実測が記述と食い違った箇所は、記事のほうを修正した
- [ ] 「前提・対象環境」に、動作対象の範囲と実際に検証した環境を分けて書いている（§12.2）
- [ ] 前提に書いたバージョンと、図のキャプションのバージョンが一致している
- [ ] 所要時間・メモリなど環境に依存する数値を本文に直書きせず、比率や桁で書いている（§12.3）
- [ ] 計測方法（試行回数・最小値か中央値か・暖機の有無）をキャプションに書いている

---

## 内部リンク（`guidelines.md` §7.1）

- [ ] サイト内リンクが canonical と同じ URL を指している（`/ja/index.html` ではなく `/ja/`）
- [ ] 記事へのリンクに末尾スラッシュが付いている（`/ja/articles/<slug>/`）

---

## フォーマットと Lint

- [ ] テーブルが含まれる場合、「ドキュメントのフォーマット」を実行してテーブル書式を統一している
- [ ] markdownlint を実行し、警告がないことを確認している

---

## AdSense 適合性

- [ ] 公式ドキュメントを超えた独自の価値を提供するコンテンツになっている
- [ ] 記事の文量が最小密度を満たしている（日本語: 700〜1,500字 / 英語: 400〜900語；文量より品質優先）
- [ ] 関連する既存記事とタイトル・概要導入文が定型的に重複していない（量産型でない。§10）
- [ ] 関連記事ごとに固有の背景・注意点・比較があり、同一言語の関連記事間で相互リンクされている（§10・§7）
- [ ] 関連記事への内部リンクが必要な箇所に含まれている
- [ ] 日本語記事と英語記事の対応するカウンターパート間に相互リンクが追加されていない

---

## フロントマター（Markdown ファイル）

- [ ] `title` が設定されている
- [ ] `date` が設定されており、UTC 日付で記載されている
- [ ] `category` が設定されている
- [ ] `excerpt` が設定されており、160字以内である
- [ ] `layout` が言語に合っている（`article-ja` または `article-en`）
- [ ] 代表となるスクリーンショットがある場合、`image` にそのサイト絶対パスが設定されている（SVG は指定しない）
