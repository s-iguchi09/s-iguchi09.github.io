# 記事執筆ガイドライン

本サイトに公開する技術記事のルール。
日本語・英語の両方の記事がこのガイドラインに従う。

---

## 1. 適用範囲

このルールはすべての技術記事に適用する。各記事は明確に定義された1つの技術テーマを扱うこと。

---

## 2. 記事構成

記事の性質に応じて、以下の 2 つの構成タイプから適したものを選ぶ。
どちらのタイプでも「概要」と「まとめ」は省略不可とし、コードを伴う記事では説明付きの実装例を含める。

### 2.1 問題解決型

特定の不具合・制約・つまずきを扱い、その原因と解決策を示す記事に適する。
以下のセクション順で構成する。「概要」「まとめ」は省略不可とし、コードを伴う場合は「実装例」も省略不可。それ以外のセクションは明確に不要な場合のみ省略可。

| # | セクション | 目的 |
|---|---|---|
| 1 | 概要 | 記事が扱う内容と解決する問題を明示する |
| 2 | 前提・対象環境 | フレームワーク、言語バージョン、アーキテクチャの前提を記述する |
| 3 | 問題 | 問題が発生する状況を具体的に説明する |
| 4 | 原因・背景 | 問題が起きる理由を説明する |
| 5 | 解決方法 | 採用するアプローチの要点を記述する |
| 6 | 実装例 | 説明を伴うコードサンプルを記述する |
| 7 | 注意点 | 制約・エッジケース・落とし穴を記述する |
| 8 | 代替案・比較 | 他のアプローチとトレードオフ表を記述する |
| 9 | まとめ | 選択基準を含む最終的な推奨を記述する |

### 2.2 手順・解説型（How-to）

明確な不具合ではなく、機能の実装手順・使い方・複数アプローチの解説を扱う記事に適する。
「問題」「原因・背景」を独立セクションとして持たず、実装アプローチごとの見出しで本文を構成してよい。
最低限、以下を満たすこと。

| # | セクション | 目的 |
|---|---|---|
| 1 | 概要 | 記事が扱う内容と、既定の挙動やなぜカスタマイズが必要かを明示する |
| 2 | 前提・対象環境 | フレームワーク、言語バージョン、アーキテクチャの前提を記述する |
| 3〜 | 本文（アプローチ別の見出し） | 各手法を、説明を伴う実装例とともに記述する |
| — | 注意点 | 制約・落とし穴を、独立セクションまたは各手法の補足として記述する |
| 末 | まとめ | 選択基準を含む最終的な推奨を記述する。比較表を推奨する |

いずれのタイプでも、§5 の必須コンテンツ要素と §6 の AdSense 適合性は満たすこと。

## 3. 文体

### 3.1 文体の基本

- 断定的・説明的な文体を使う。
- 三人称または無主語構文で記述し、読者への直接的な呼びかけは避ける。
- 書き言葉の丁寧体ではなく、形式的な書き言葉（常体）を使う。

**日本語の例:**

| 避けること | 代わりに使う表現 |
|---|---|
| はい、対応できます。 | 対応可能である。 |
| 結論としては、 | （削除して断定文にする） |
| つまり、 | このため / 問題の本質は / したがって |
| 〜してみましょう | 〜を実施する |
| 〜するとよいでしょう | 〜が適切である / 〜が適する |
| 便利です | 有効である |
| わかりやすいです | 把握しやすい |
| 〜になります | 〜となる / 〜である |

**英語の例:**

| 避けること | 代わりに使う表現 |
|---|---|
| Let's try… | To implement… |
| It's easy to… | The approach is… |
| You can just… | This can be achieved by… |
| It's useful | This is effective for… |
| As you can see… | The result shows… |

### 3.2 見出し

- 見出しは名詞句または動詞句を使い、疑問文にしない。
- Q&A形式の見出しは不可。

| 避けること | 代わりに使う表現 |
|---|---|
| なぜ起きるのか？ | 原因 |
| 対応できるか？ | 対応方法 |
| Shift 範囲選択にも対応できるか | Shift 範囲選択への対応 |

### 3.3 1記事1テーマ

記事は明確に範囲が定義された1つの技術テーマを扱うこと。独立した複数のトピックを1記事にまとめない。

---

## 4. コードスニペット

すべてのコードブロックの前後に説明文を記述すること:

- **コードの前:** そのコードが何をするのか、なぜこのアプローチを使うのかを説明する。
- **コードの後:** 制約・注意点・期待される動作を説明する。

コードが大部分を占め説明文が最小限の記事は不可。

---

## 5. 必須コンテンツ要素

各記事に含めるべき内容:

- **前提・対象環境** — フレームワーク、バージョン、アーキテクチャ（例: MVVM、コードビハインド）を明記する。
- **原因・背景の説明** — 「何をすべきか」だけでなく「なぜそうなるのか」を説明する。
- **選択基準** — どの条件でどのアプローチが適切かを明示する。
- **制限事項** — ソリューションが対応しない状況や機能しなくなる条件を記述する。
- **推奨を含むまとめ** — どの条件でどのアプローチを選ぶべきかの最終的な推奨で締める。

---

## 6. AdSense 適合性

記事には Google AdSense が掲載される。以下を守ること:

- 公式ドキュメントを超えた独自性のある内容を提供すること。
- 推奨最小文量: 約700〜1,500字（日本語）または400〜900語（英語）。文量より品質・密度を優先する。
- 比較表・落とし穴・実用的な選択ガイダンスのうち、少なくとも1つを含めること。
- 公式ドキュメントを言い換えるだけの薄いコンテンツは公開しない。

---

## 7. 内部リンク

関連記事がある場合は本サイト内の記事へのリンクを含めること。

- 日本語記事と英語記事の対応するカウンターパート間には相互リンクを追加しない。

### 7.1 リンク先は正規 URL にする

サイト内リンクは、そのページの `canonical` と同じ URL を指すこと。

- 記事へのリンクは `/ja/articles/<slug>/` のように**末尾スラッシュ**を付ける。
- ディレクトリの既定ページは `/ja/` のように参照する。**`/ja/index.html` と書かない。**

`/ja/index.html` と `/ja/` はどちらも 200 を返す同一内容であり、前者は後者へ `canonical` している。
サイト共通ヘッダーがこの前者を指していた。ヘッダーは全ページに出るため、**サイト内で最も本数の多い内部リンクが、正規 URL ではないほうを向いていた**ことになる。

`/ja/` へのリンクが皆無だったわけではない。記事ページのパンくずは `/ja/` を指しており、こちらは正規 URL 側に入っていた。
それでも、全ページに出るヘッダーが重複 URL を指す状態は、評価が 2 つの URL に分かれるため解消する価値がある。

日本語トップページ（`/ja/`）は「クロール済み - インデックス未登録」と判定されていた。
ヘッダーのリンク先がその原因であったことを Search Console から確かめる手段は無いため、
**原因になりうる状態を解消した**という位置づけで扱う（2026-08-29 に修正）。

## 8. タイトル

タイトルは技術テーマが即座に伝わるものにする。

| 避けること | 代わりに使う表現 |
|---|---|
| DataGrid を便利に使う | WPF DataGrid の並び替えを実装する方法 |
| WPF の小技 | WPF ListBox の仮想化環境における選択状態の管理 |
| Useful Tips for WPF | Implementing Column Sorting in WPF DataGrid |

## 9. Markdown フォーマットと Lint

- 文末ごとに改行を入れる。
  - 日本語記事: `。` などの句点で改行する。
  - 英語記事: `.`、`!`、`?` などの終止符で改行する。
  - 読点・カンマでは改行しない。
- 記事にテーブルが含まれる場合は、フォーマットを整えるため「ドキュメントのフォーマット」を実行する。
- 編集を確定する前に markdownlint を実行し、警告がないことを確認する。
  - ただし `MD060`（テーブル列の整形スタイル）は本リポジトリでは無効とする（`.markdownlint.json` で `false`）。従う必要はない。

---

## 10. シリーズ記事・関連記事の差別化

同一領域で複数の関連記事を作成する場合、量産型コンテンツ（同一テンプレートのバリエーション違い）と見なされないよう、各記事の独自性を明示する。これは Google AdSense の「スケール化されたコンテンツの不正使用」への該当を避けるためのルールでもある。

- タイトルは連番（「〜を X 版で」「〜を .NET X 相当に」など）ではなく、各記事固有のテーマ・対象（扱うメソッド名や機能名など）を主体にする。
- 概要冒頭の導入文をテンプレートとして使い回さない。各記事が扱う対象に即した独自の切り口で書く。
- 前提・実装例など構成が共通化する場合でも、各記事に固有の背景・注意点・比較を含める。
- 同一言語の関連記事どうしは相互リンク（§7）で結び、「シリーズ」としての文脈を与える（日英の対応するカウンターパート間にはリンクを張らない。§7）。

## 11. 図・スクリーンショット

記事には、文章とコードだけでは伝わらない内容を補う図やスクリーンショットを添える。とくに実際に動作させた画面のキャプチャは、記事が実体験に基づくことを示す材料になる。

### 11.1 素材の選び方

- **実行結果が画面に現れるテーマ** — 実際にアプリケーションを動かしたスクリーンショットを使う。モックアップや作図で代用しない。
- **画面に現れないテーマ**（データフロー、ライフサイクル、状態遷移など） — 概念図を SVG で作成する。
- 全記事に同じ種類の図を同じ位置へ機械的に入れない。テンプレートを流用した量産型コンテンツと見なされる要因になる（§10 と同じ趣旨）。記事ごとに必要な図を選ぶ。
- 図の内容が本文の記述と食い違わないよう、**図は本文に載せたコードと同じ条件で生成する**。

### 11.2 スクリーンショットの生成

記事用のスクリーンショットは `tools/screenshot-capture` の WPF アプリで生成する。記事ごとにシーンを追加し、コマンドで再生成できる状態を保つ。手順は [`tools/screenshot-capture/README.md`](../../../tools/screenshot-capture/README.md) を参照する。

- 記事の主張（「この設定だと表示が変わる」など）は、図を作る前に実際に動かして確認する。
- 確認の結果、記事の主張が再現しなかった場合は、**図を省略するのではなく本文を修正する**。誤った主張に図を添えると誤りを補強することになる。前提そのものが崩れている場合は、実機の挙動に合わせて記事を書き直す。
- 撮影環境（`.NET` のバージョン、OS）はキャプションに明記する。実測値を載せる場合は、テーマ・`ControlTemplate`・入力データなど結果を左右する条件も併記し、絶対値ではなく比率として読める書き方にする。

### 11.3 保存先とパス

- 保存先は `images/articles/<slug>/` とする。日英で同じ画像を共有するため、言語別のディレクトリは作らない。
- 本文からの参照は **`/images/articles/<slug>/<file>` の形式のサイト絶対パス**にする。相対パスにすると `sitemap.xml` の `<image:image>` に収集されない。
- **形式は原則 SVG とする。** 拡大しても文字がぼやけず、ファイルが小さく、差分で値の変化が読める。
- **PNG を使うのは、実行中のウィンドウそのものを見せる図に限る。** コントロールの描画結果を示す図は、実際のウィンドウをキャプチャした PNG でなければ意味がない（§11.1 のとおり、作図で代用しない）。
- 実測値の表は SVG にする。表は文字と罫線だけで構成されるため、ウィンドウを撮影せずに直接描ける。`SceneContext.SaveTableAsync` が実測値から SVG を生成する。ウィンドウを表示しないため、ディスプレイの電源状態にも影響されない。
- 幅は 880px 以下を目安にする。

### 11.4 本文への埋め込み

`figure` 要素で囲み、`figcaption` に説明を書く。`_config.yml` で `hard_wrap: true` を設定しているため、**前後に必ず空行を置く**（空行が無いと直前の文と連結されて `<br />` になる）。

```html
<figure class="article-figure">
  <img src="/images/articles/<slug>/<file>.png" alt="（画像の内容を説明する代替テキスト）" width="461" height="166" loading="lazy">
  <figcaption>（図が何を示しているかの説明。撮影・生成した環境を含める。）</figcaption>
</figure>
```

- `alt` は必須とする。装飾ではなく内容を説明する文にする。
- `width` / `height` には実際のピクセル寸法を指定する（表示のずれを防ぐため）。
- `loading="lazy"` を付ける。
- 本文幅（およそ 860px）より横に広い図は `class="article-figure article-figure--wide"` とする。狭い画面で図の内側だけが横スクロールする。
- **日英で同じ画像を使い、`alt` と `figcaption` のみ各言語で書く。** 画像の中に文言を入れる場合は、コード識別子など言語に依存しない表記に留める。
- 記事を代表するスクリーンショットがある場合は、front matter に `image: /images/articles/<slug>/<file>.png` を設定する。構造化データの `image` として出力される。Google の Article 構造化データは SVG をサポートしないため、**`image` には SVG を指定しない**。図が SVG しか無い記事では `image` を設定しない。

## 12. 主張の検証

記事に書く技術的な主張は、**実際に動かして確認したものだけ**にする。
公式ドキュメントの読解や一般的な知識だけを根拠にした断定は書かない。

このルールは 2026-08-29 に追加した。Search Console で「クロール済み - インデックス未登録」と判定された記事を実測で検証したところ、前提と図でフレームワークのバージョンが食い違う、計測していない性能差を断定している、推奨した実装が実際には期待どおり動かない、といった誤りが複数見つかったためである。
いずれも読者がコードを試せば分かる種類の誤りであり、**文章のレビューだけでは検出できない**。

### 12.1 検証の必須化

- 記事の主張は、`tools/screenshot-capture` に**シーンとして実装し、実行して確認する**。シーンは記事と同じ PR でコミットし、`dotnet run --project tools/screenshot-capture -c Release -- <slug>` でいつでも再現できる状態にする。
- **概念図（SVG）は説明であって検証ではない。** 図がデータフローや状態遷移の作図だけの場合、その記事の主張は検証されていない。実行結果が画面や数値に現れるテーマでは、必ず実行して確かめる。
- 動かして確認できなかった主張は**書かない**。削るか、確認していない旨を本文に明記する。
- 確認の結果が想定と異なった場合は、**記事の結論のほうを変える**。実測に反する記述を残さない（§11.2 と同じ趣旨）。
- 生成した画像は目視で確認する。ツールは失敗せずに中身が白紙の画像を出力することがある（`tools/screenshot-capture/README.md`）。

### 12.2 検証環境の明記

「前提・対象環境」には、**動作対象の範囲**と**実際に検証した環境**を分けて書く。両者は同じとは限らない。

```text
- フレームワーク: .NET 6 以降 / WPF                ← 動作対象の範囲
- 検証環境: .NET 10 / Windows 11                   ← 実際に動かした環境
- 追検証: .NET Framework 4.8 でも同一の結果を確認  ← 任意
```

図のキャプションにも撮影・生成した環境を書く（§11.2）。
**前提に書いたバージョンと図のキャプションのバージョンを食い違わせない。**

### 12.3 実測値の扱い

数値を伴う主張は、**種類を問わずシーンで計測する**。目で数えた値や、手元で一度動かしただけの値を本文へ書かない。
そのうえで、環境に依存する数値は図に出力し、本文へは直書きしない。

- 所要時間・メモリ使用量など**実行環境に依存する値**は、本文では比率や桁で書く（「約 2 倍」「2 桁大きい」）。絶対値は図に持たせる。本文に絶対値を固定すると、環境が変わった時点で誤りになる。
- 図はキャプチャのたびに再計測されるため、本文を比率で書いておけば両者が食い違わない。
- **環境に依存しない決定的な値**（visual ツリーの要素数、実体化されるコンテナ数など）は本文に書いてよい。ただし**値そのものはシーンで求める**。決定的な値でも、visual ツリーを目で追うと子コントロールのテンプレート部品まで数えてしまうなどの誤りが起きる。判別条件（`TemplatedParent` が対象コントロール自身か、など）をコードに書けば、次に確かめ直しても同じ結果になる。
- 計測方法をキャプションに明記する（試行回数、最小値か中央値か、暖機の有無）。
- 条件を交互に試行して実行順の影響を避ける、暖機して JIT の影響を外すなど、**結果を左右する手順はシーン側に実装する**。図の再現性はシーンのコードで担保する。

### 12.4 検証したことをシーンに宣言する

シーンが「実際に動かして確かめていること」を `IScene.Verifies` に書く。
実行すると `docs/verification/<slug>.yml` へ、確かめた内容・実行環境・生成した図が自動で書き出される。

```yaml
slug: "wpf-binding-error-debugging-output-window"
scene: "BindingErrorTraceScene"
environment:
  runtime: ".NET 10.0.10"
  os: "Microsoft Windows 10.0.26200"
verifies:
  - "パス解決失敗が Error 40、ConvertBack 失敗が Error 7 であること"
images:
  - "images/articles/.../binding-error-trace-matrix.svg"
```

**目的は、同じ検証を何度も繰り返さないことである。**
記事の書式（`検証環境` の行があるか、PNG を参照しているか）から「検証済みか」を推測すると、書き方の違いで検証済みの記事を未検証と誤判定する。
実際にそれが起きて、既に実測した記事を再検証したことがある。

このファイルは手で編集しない。内容を変えるにはシーンの `Verifies` を直して再実行する。
`docs` は `_config.yml` の `exclude` に入っているため、サイトには出力されない。

**`Verifies` には、そのシーンが実際に測っていることだけを書く。**
記事に書いた主張のうち、シーンが実行していないものを `Verifies` に含めてはならない。
「実測した」と書きながらシーンは別の経路しか通っていない、という食い違いが起きる。
主張を残すのであれば、その主張を測るケースをシーンへ追加する。

図を描くだけで何も検証していないシーンは `Verifies` を空のままにする。その場合は記録も作られない。
